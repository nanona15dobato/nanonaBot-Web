# タスク全体のウェーブと呼び出し先のpurge

新しく作るタスクは `workflowVersion: global-v1` を保存し、ルールの種別ではなく「Template／通常ページ」で共通の段階を組みます。たとえば同じ記事の `{{旧テンプレート}}` と `[[旧リンク]]` を変える場合、両方の取得対象に入る記事は1つの準備済み本文にまとめ、1回の差分確認・編集で保存します。

## 処理順

1. **全ルールのTemplate対象をまとめて編集する。** リンク・外部リンク・Category系はTemplateを先行対象にします。テンプレート置換、リンク解除、subst、カスタムは、選択された範囲にTemplateが含まれる場合にここで処理します。
2. **実際に編集したTemplateの呼び出し先を更新する。** `embeddedin` で呼び出し先を全名前空間から取得し、重複を除いてpurgeします。対象は編集したTemplate本体ではなく、呼び出しているページです。初期設定はオン・`purge＋forcelinkupdate`。無効にするかnull editを選ぶこともできます。
3. **通常ページの対象を取り直してまとめ編集する。** Templateを除く選択名前空間の候補をルールごとに取得します。Category系は標準名前空間の「リダイレクトの所属カテゴリ」や、任意の一般記述の候補もここで取得します。同じページなら通常のカテゴリタグと所属カテゴリ引数を一度の編集で変更します。
4. **任意で、残る参照候補をもう一度purgeする。** 編集後に旧リンク元、旧カテゴリメンバー、旧テンプレート使用ページ、旧URLの参照等を再取得します。候補を統合して一度だけpurgeし、参照が消えるまで反復しません。初期設定はオフです。
5. **結果を確定する。** 本編集の失敗はページ・編集ログに、更新の個別失敗は更新チェックポイントと実行ログに記録します。最後にタスクの状態を確定します。

purgeはリンク表・カテゴリ所属等の再計算を促す処理です。本文の置換や差分承認ではなく、索引や参照一覧が即時にすべて更新される保証でもありません。[MediaWikiのpurge仕様](https://www.mediawiki.org/wiki/API:Purge)と[呼び出し先取得の仕様](https://www.mediawiki.org/wiki/API:Embeddedin)も参照してください。

## まとめ編集の範囲

- 同じタスク・同じウェーブ・同じタイトルを対象取得したルールを統合します。ルールの設定順で正規表現ステップを適用し、その後に所属カテゴリ引数等の構造編集を行います。
- あるルールの対象ではないページに、そのルールまで無条件に適用することはありません。名前空間や取得条件が別なら、その条件も尊重します。
- Templateを第1ウェーブへ固定し、通常ページの第2ウェーブには再登場させません。Categoryの通常メンバーと特殊参照は第2ウェーブに集約します。
- 別々のタスクを横断して合体する機能ではありません。競合後の再確認・再試行などで複数の保存試行になる場合もあります。
- 手入力やAPI結果で名前空間が不明な場合はページ情報を確認して振り分けます。確認できないまま標準名前空間と推測して編集を進めません。

## 画面とAPIの設定

| 作成画面の項目 | `editSettings` のキー | 初期値 |
|---|---|---|
| Template編集後、その呼び出し先のリンク表・カテゴリ所属を更新する | `refreshTemplateTransclusions` | `true` |
| Template呼び出し先の更新方法 | `linkUpdateMethod` | `purge`（`nullEdit`も可） |
| 編集後も残る参照候補をもう一度purgeする | `purgeRemainingTargets` | `false` |

設定はアカウントごとの既定値保存・タスク複製でも引き継ぎ、作成前の確認とタスクの設定欄に表示します。旧設定に `linkUpdateMethod: nullEdit` が保存済みなら、読み込み時にその値を維持するため、purgeへ変える場合は画面で選んで保存してください。

残存候補の再取得では検索絞り込みを外し、元の参照一覧を調べます。Templateの先行対象も含めて取得し、重複は一度だけ更新します。カスタムの手入力と固定対象は、残存参照を調べる取得元ではないため最終purgeに含めません。

## 中断・失敗・上限

- `target_titles_json` の `templateRefresh` と `remainingRefresh` に、それぞれの対象一覧・進捗を保存します。purgeは最大50件、null editは1件ずつ更新し、バッチごとに保存します。完了後は対象一覧を消し、完了印・総数・失敗数・方法を残します。
- 緊急停止・中止を取得の間、更新バッチ前、待機中に確認します。対象取得の途中で停止した場合は、不完全な一覧を完了扱いで保存せず、再開時に取得し直します。更新中なら保存済みの次から再開します。
- 送信済みの更新を通信途中から取り消す機構ではありません。更新とチェックポイント保存の間でクラッシュすると、最後の更新が再度送られる可能性があります。
- 個別更新の失敗は警告として残して続行します。対象取得が例外で失敗した場合は、通常のワーカーのエラー処理でタスクが失敗になります。本文が保存済みの場合はその結果が残ります。
- 呼び出し先・参照候補の取得には既存の取得上限があります。打ち切りや検索警告があればログに残し、取得できた候補だけを更新します。

## 既存タスクとの互換性

`workflowVersion` のない既存タスクの途中再開では、保存済みの種別別ウェーブを維持します。作業行の途中でウェーブ番号の意味を変えて再編集しないためです。新構成を使う場合は複製して新しいタスクを作ります。

失敗ページの再試行と一括取り消しは、固定対象の1ウェーブを維持し、呼び出し先更新・最終残存purgeを実行しません。全体ウェーブだけならDB変更は不要ですが、一時停止・途中変更を含む更新では[専用マイグレーション](task-controls.md#導入更新)が必要です。

## 確認方法

- テンプレート置換＋リンク置換の混在記事が1回の編集で両方変わること。
- Categoryタグ＋「リダイレクトの所属カテゴリ」の引数が同じ記事の1回の編集で変わること。
- Template編集→呼び出し先purge→通常候補の再取得→通常編集→任意の残存purge、の順番になること。
- 更新設定のオン／オフ、既定値保存、複製、停止後の続行、旧タスクの再開がそれぞれ設定どおりになること。

`test/globalWaves.test.js` は実際のパイプラインと模擬DB・Wikiを組み合わせてこの順番と編集回数を検証します。ブラウザ側の設定確認は、別途用意したPlaywrightで次を実行します。

```sh
PLAYWRIGHT_MODULE_PATH=/path/to/playwright node scripts/check-global-waves-ui.js
```

本番反映は実行中の処理が一区切りした時点で行い、反映中は新しいタスクを作成せず、Webとワーカーの双方を再起動してから新規タスクを作成してください。実ウィキでのpurge結果・索引反映は模擬テストと別に確認します。
