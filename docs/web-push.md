# 端末へのWeb Push通知（PWA 第2段階）

オーナーが端末ごとに通知を有効化し、Botの緊急停止・タスクの停止や完了を受け取る。既存のメール／Webhook通知とは独立して設定する。Wikimedia自身の通知・ウォッチリストを取得する機能は含まない。

## 利用方法

1. 必要に応じてアプリをインストールし、オーナーとしてログインする。iPhone/iPadではホーム画面に追加したアプリから開く。
2. 設定画面の「この端末への通知」で対象イベントを選ぶ。既定は「タスクの完了」以外の7種類。
3. 「この端末で通知を受け取る」を押したときにだけ、ブラウザの許可を求める。画面表示時には求めない。
4. 有効化後の変更は「通知する出来事を保存」で保存する。すべて外すと通常のイベント通知を送らない。
5. 「この端末へテスト通知」は、この端末だけに選択イベントと無関係なテスト通知を送る。「送信しました」はPushサービスが受け付けた意味で、実際の端末表示は利用者が確認する。
6. 停止は「この端末の通知を停止」。ブラウザのサイト設定から許可自体を取り消すこともできる。

通知には常に「確認が必要なイベントがあります」という汎用の本文を使い、ページ名・利用者名・エラー詳細をロック画面へ出さない。通知を押すと対象タスクまたは設定・ホーム画面を開く。実行・停止などの操作ボタンは通知に置かない。未ログインなら通常のログイン画面を表示する。

通知の配送には、ブラウザ提供元のPushサービスを使用する。本文はWeb Pushの標準方式で暗号化する。通知購読とサイトの通知許可はブラウザが管理し、アプリはlocalStorage・IndexedDB・Cache Storageに購読情報を保存しない。

## ログインと購読の寿命

- 購読は有効化したときのユーザーとサーバー側ログインセッションに紐付ける。
- 送信時に、セッションの存在・期限・ユーザー名・ownerロール・現在のオーナー設定を確認する。
- ログアウトではそのセッションのDB購読を削除し、ブラウザ側の解除と表示済み通知の消去も試す。ブラウザの解除が止まっても、1秒で待ちを切り上げサーバーのログアウトを進める。
- DB購読の削除に失敗しても、セッションが破棄されれば以降の送信対象から外れる。
- セッション期限（現在の既定7日）またはブラウザの購読期限まで有効。再ログイン後は端末で明示的に有効化する。
- 期限切れ・存在しないセッション・変更前のVAPID公開鍵の購読を、送信／登録の際に整理する。Pushサービスから404/410を受けた購読も削除する。
- 購読変更をバックグラウンドで検知しても自動再購読せず、設定画面からの再確認を案内する。
- すでに送信された通知は完全には取り消せない。Pushサービスでの保存期間は60秒とし、ログアウト直前の通知などが遅れて届く場合がある。

セッションの存在・ロール変更を送信時に確認するが、送信中の通知を遡って取り消すものではない。環境変数でオーナー設定を変えた場合は、Webサーバーとワーカーの両方を再起動する。

## サーバー設定

| 環境変数 | 内容 |
|---|---|
| `VAPID_SUBJECT` | 運用者の連絡先。`mailto:`のメールアドレス、または連絡先を示すHTTPS URL |
| `VAPID_PUBLIC_KEY` | VAPID公開鍵。設定画面にはオーナーに対してのみ公開する |
| `VAPID_PRIVATE_KEY` | 対応する秘密鍵。レスポンスやログには出さない |

3つが揃い、鍵ペアが正しいときだけ有効になる。未設定でも既存のWeb画面・メール／Webhook・Bot処理は継続する。送信先URLはFCM、Mozilla、Apple、Microsoftの所定のHTTPSホストに限定し、任意のURLや内部ネットワーク宛てには送らない。リダイレクトには追従しない。

送信対象の選択に `NOTIFY_EVENTS` は使用しない。端末ごとの選択を使用する。メール／Webhookの設定画面にある従来の「テスト送信」は、従来の2経路だけを対象とする。

## 本番反映

1. マージ済みmainを取得する。
2. Nodeの実行環境で `npm install --ignore-scripts --omit=dev --no-audit --no-fund` を実行し、追加依存の `web-push` 3.6.7を用意する。本番の未追跡lockfileが更新された場合は別途レビュー・保管する。
3. 対象ToolsDBを選択し、`db/migrations/20261025_push.sql` を実行する。購読テーブルの追加のみで、既存データは変更しない。新規環境では `db/schema.sql` にも含まれる。
4. Nodeの実行環境で次を1回だけ実行して、鍵ペアを生成する。

   ```sh
   node node_modules/web-push/src/cli.js generate-vapid-keys --json
   ```

   **秘密鍵を含む出力をチャットやログ共有へ貼り付けない。** 鍵は保管し、再起動のたびに再生成しない。
5. bastionの `toolforge envvars create` で上記3変数を登録する。Webとワーカーに同じ鍵ペアを渡す。
6. Webサーバーを再起動する。待機中のワーカーも `toolforge jobs restart nanona-bot-worker` で再起動し、新しい通知処理と環境変数を読み込む。
7. ブラウザでアプリを開き直す。更新案内があれば更新する。第1段階の古いService Workerが動いている間は通知の有効化を受け付けない。
8. 端末で明示的に通知を許可し、テスト通知の実受信を確認する。Toolforgeから各Pushサービスへの到達性、端末側設定、iPhone/iPad実機での表示は本番反映後に確認する。

鍵を変更すると既存端末は再登録が必要になる。登録時には画面が取得した公開鍵が現在のサーバー設定と一致することも確認し、変更前の画面からの登録は受け付けない。VAPIDの設定値、購読のendpoint・auth・p256dh、セッションIDを調査出力に含めない。テーブルの準備確認は `SHOW TABLES LIKE 'push_subscriptions';` など、本文を出さない方法で行う。

## 動作上の限界

通知は配送や即時表示を保証しない。OSの通知設定・集中モード・ネットワーク状態で遅延や非表示になる。通知を緊急停止そのものや唯一の監視経路として扱わず、必要に応じ既存メール通知も併用する。

各送信では最大100件を選び、同時送信4件・通信の総時間5秒の範囲で処理する。失敗を自動再送しない。同じイベントと対象の通知は同じtagでまとめる。購読上限はユーザーごとに20端末を目安に制限する（同時登録の厳密なレート制御ではない）。

## 検証

Nodeテストは、購読入力、暗号化とVAPID署名、期限と権限、送信先制限、他セッションへの操作防止、ログアウト、失敗時の既存通知継続、Service Workerの汎用表示と遷移先制限を扱う。外部へ実際の通知は送らない。

`scripts/check-push-ui.js` は検証用Playwright/Chromiumで設定画面を動かす。通知API・購読・サーバー応答は模擬し、初回の無断許可要求がないこと、有効化／イベント選択／テスト送信／停止、古いworkerや非対応ブラウザ、許可拒否、ブラウザ解除が停滞してもログアウトできることを確認する。

```sh
PLAYWRIGHT_MODULE_PATH=/path/to/playwright node scripts/check-push-ui.js
```

実際のPushサービスを通した受信とSafari実機確認は、この模擬テストとは別に行う。

参考: [web-pushの公式ドキュメント](https://github.com/web-push-libs/web-push)、[AppleのWeb Push説明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)、[Toolforgeのジョブ再起動](https://wikitech.wikimedia.org/wiki/Help:Toolforge/Running_jobs#Restarting_your_jobs)。
